Part A: understand the project

1. The 2-minute pitch

Problem. Party games played on phones break in the ways that matter at a real game night: a phone locks or the Wi-Fi drops and you come back as a new player with zero points (the skribbl.io complaint the SPEC names), one person has to stay the "host", and secret information leaks or relies on trust.

Who it's for. Indian friend groups (hostel rooms, Friday nights). Everyone plays on their own phone; a laptop or TV can join as a display-only big screen. Content is India-aware: Bollywood, cricket, Indian cities, Hinglish prompts.

What it is. A phone-first web app (installable PWA) with nine games: Quiz Clash, Dumb Charades, Draw & Guess, Atlas, Imposter, Most Likely To, Name Place Animal Thing, Emoji Decode and Two Truths & a Lie. You join with a 4-letter code, a link, or a QR code, with no account needed.

What makes it stand out.

  • The server is the referee. Every action is validated on the server, applied to one versioned state document under a row lock, and only then broadcast. Secrets (quiz answers, the draw word, the imposter) are filtered per viewer, so nobody can cheat by inspecting the network.
  • Rejoin keeps everything. A phone that locks, refreshes, loses Wi-Fi or closes the tab comes back to the same seat, score and countdown.
  • Hostless. Server-side deadlines move the game on, AFK players are skipped after two missed turns, and admin passes automatically after 60 s.
  • Memory. Crews get a monthly season leaderboard, head-to-head records and end-of-night awards.
  • Evaluable alone. /demo gives one person a room with 4 bots for every game.

Proof. 103 requirements and 103 acceptance criteria. 234 unit tests and 57 multi-phone E2E tests, each run on Android Chromium and iPhone WebKit. Production checks from a GitHub-hosted runner show update latency p95 of about 200 ms against a 1 s budget.

Live: https://playhuddle.vercel.app (try /demo).

2. Architecture

One Next.js app on Vercel serves the UI and the API. All game logic lives in pure TypeScript modules with no I/O. Postgres (Neon) holds the authoritative state, and Ably fans updates out to the phones. Clients only subscribe; the server does all publishing.

End-to-end flows

(a) Joining a room

  1. Phone: JoinScreen in src/client/components/RoomClient.tsx. If the typed name differs from the current identity, it calls POST /api/identity/guest, which runs ensureGuest() in src/server/identity.ts: it creates an identities row and sets the huddle_dt cookie (httpOnly, SameSite=Lax, 1 year, holding a random 32-byte token stored only as a SHA-256 hash).
  2. Route: POST /api/rooms/[code]/join with an x-huddle-device header goes to src/app/api/rooms/[code]/join/route.ts, which calls getIdentity().
  3. Handler: roomOp(code, identity, op) in src/server/rooms.ts opens a transaction and runs SELECT … FOR UPDATE on the room row, then prepare() loads presence, ratings and reported questions, then catchUp() processes anything overdue.
  4. Module: joinRoom() in src/engine/room.ts. An existing seat for any of the identity's aliases is a rejoin: the same seat and score come back. Otherwise a new seat is created, or the newcomer becomes a spectator if a game is running (seated at the next round, R9) or 12 players are seated.
  5. Database: the state changed, so the version goes up by 1 and rooms.state and version are written. Then presence is upserted and the transaction commits.
  6. Ably: after the commit, publish(roomId, 'state', {v, serverNow, public, privateFor}) sends the public view only.
  7. Every phone: RoomSync.onStateMessage applies it if v = local + 1. A gap fetches a snapshot, and a seat listed in privateFor fetches its private view over HTTPS. The joining phone itself starts RoomSync.start(): it fetches a snapshot through touch() / peekRoom(), then connects to Ably with authUrl=/api/realtime/token?code=….

(b) Submitting a quiz answer

  1. Phone: QuizGame.tsx calls answer(i), which calls sync.act('answer', {choice}). That generates a UUID actionId and sends POST /api/rooms/[code]/actions with a 30 s timeout, retrying once with the same actionId.
  2. Route: actions/route.ts validates the UUID and type, then calls roomOp(..., {actionId, type}).
  3. Handler: it locks the row. If room_actions already has this (room_id, action_id), it returns the stored result (idempotent replay). Otherwise it runs catchUp().
  4. Module: applyAction() calls rateLimit() (10 actions/s per seat), clears AFK, then dispatchGame() calls quiz.act() in src/games/quiz/rules.ts. That checks the phase is question and choice is 0–3, makes the first tap final, records ms = now − phase.startedAt, and calls reveal() early once every active player has answered. Points are 500 + round(500 × remaining / duration).
  5. Database: it writes the state with version + 1, inserts into room_actions with the result, and commits.
  6. Ably: it publishes the public view. During the question that view contains answeredSeatIds but no correct option; reveal is non-null only in the reveal phase (R34). privateFor lists the answering seat, because its myChoice changed.
  7. Every phone: the "n / m answered" count updates. The answering phone refetches its private view, though its tap is already shown as pending in the UI.

(c) A drawing stroke

  1. Phone (drawer): src/client/games/draw/Canvas.tsx uses pointer events with touch-action: none. It flushes every 200 ms or at 64 points, simplifying each segment with Ramer–Douglas–Peucker (rdp() in src/lib/strokes.ts, ε = 0.75 units on a 1000 × 750 canvas), and sends POST /api/rooms/[code]/strokes {turnId, seq, ops}.
  2. Handler: appendStrokes() in src/server/strokes.ts does not lock or version the room row. It reads the state, checks the seat, validOps and canDraw() (draw phase, current drawer, current turnId), that the batch is at most 8 KB, and that the room has sent at most 8 batches in the last second.
  3. Database: INSERT INTO strokes … ON CONFLICT DO NOTHING makes a duplicate seq harmless.
  4. Ably: if the row was inserted, it publishes a strokes message.
  5. Every phone: onStrokes passes it to the Canvas, which renders the batch. A gap in seq, or any applied snapshot (onCatchUp), triggers GET strokes?turnId&after=lastSeq, so a reloaded phone gets the full drawing.
Snapshot, tick and heartbeat all go through touch() in src/server/touch.ts. It first tries peekRoom(): an unlocked read that runs catch-up on a copy and returns at once if nothing is due. Only if something changed does it fall back to the locked roomOp. This came from a production finding: every phone's no-op requests were queueing on the row lock.

4. Data model and key algorithms

Postgres tables (db/migrations/001_core.sql)

users, identities (guest or user; device_token_hash; merged_into), crews, crew_members, rooms (state jsonb, version, expires_at, ended_at), room_actions (idempotency and audit; unique per room and action id), presence (heartbeats, kept apart so they never lock the room row), strokes (append-only per turn), games, game_results, nights, ratings, question_reports, place_suggestions.

The room state document (RoomState in src/engine/types.ts) is one JSON value per room, holding status, seats, teams, queue, phase {id, kind, deadline, startedAt, durationMs, turnSeatId}, paused, game (module state), scoreEvents, botPlan, notices, memory and the rate buckets. It is changed only inside the row-locked transaction, and its version equals rooms.version.

Algorithms with worked examples

Clock offset (src/client/clock.ts)

offset = serverNow − (tSend + tRecv) / 2, taken from the sample with the lowest round trip among the last 5. Example: sent at 1000, received at 1200 (RTT 200), serverNow 5,000,100 gives offset 4,999,000. The countdown shows ceil((deadline − (Date.now() + offset)) / 1000). To decide that a deadline has passed it uses safeNow, a lower bound of serverNow − tRecv (here 4,998,900), so a phone never ticks early. Ticks also add 0–300 ms of random jitter.

Placement points (engine/core.ts placementPoints)

pp = round(100 × (n − p) / (n − 1)); tied units get the average of the positions they cover. For 4 players with scores 900, 700, 700, 100: positions 1, (2+3)/2 = 2.5 and 4 give pp = 100, 50, 50, 0.

Multiplayer Elo (engine/elo.ts eloDeltas)

For each pair, E = 1 / (1 + 10^((Rj − Ri)/400)) and S ∈ {1, ½, 0}; ΔRi = (32 / (n − 1)) × Σ(S − E). With two 1000-rated players, E = 0.5, so the winner gets 32 × (1 − 0.5) = +16 and the loser −16 (AC-37).

Team balancing (engine/teams.ts balanceIndices)

Sort by strength, snake-draft (1-2-2-1…), then repeatedly apply the single swap that most reduces max(mean) − min(mean). Ratings 1400, 1300, 1200, 1100, 1000, 900 into 2 teams give {1400, 1100, 1000} (mean 1166.7) and {1300, 1200, 900} (mean 1133.3), a 33.3-point gap. No swap does better, which matches AC-35's "within 34". Strength is this game's rating, else the mean of the player's other ratings, else 1000 (strengthFor).

Catch-up with a virtual clock (catchUp)

If nobody's phone was open for three turns, the next request processes all three overdue deadlines in order, each at its own due time, so the AFK and turn logic behaves as if someone had ticked each one. The cap is 50 steps. Before that, autoPause stops a silent room (over 120 s) from fast-forwarding.

Stroke simplification (lib/strokes.ts rdp)

Ramer–Douglas–Peucker keeps a point only if it is more than ε = 0.75 units from the simplified chord. The tested invariant (AC-64) is a Hausdorff distance of at most 1 unit between raw and simplified lines, with at least 40 % fewer points on average. Points are integers, delta-encoded [x0, y0, dx1, dy1, …].

Idempotency

Each action carries a client UUID. room_actions has a unique key on (room_id, action_id) and stores the result, so a retried request returns the original answer without applying it twice (AC-14: the same id posted twice applies once; 20 concurrent distinct actions raise the version by exactly 20).

Text matching (lib/text.ts)

fold() strips accents, case, spaces and punctuation, so "Auto-Rickshaw", "auto rickshaw" and "autorickshaw" all match. isClose is edit distance 1, or 2 for words of 8+ letters (Draw's "You're close"). Atlas and NPAT look places up by folded name or alternate name.

6. The SDD process

  • SPEC.md is the contract. Requirements use EARS patterns (Ubiquitous "The system shall…", Event "When…", State "While…", Unwanted "If…, then…", Optional "Where…"), each tagged Must or Should. Acceptance criteria AC-n are pass/fail checks tagged Unit, E2E, Deploy or Manual, each mapped to requirements. Now: 103 requirements (95 Must, 8 Should) and 103 ACs (47 Unit, 47 E2E, 7 Deploy, 2 Manual).
  • PLAN.md turns that into phases 1–17. Each has tasks, the ACs that prove it ("Done when") and the commands to run. It also holds an AC status table with evidence, a decision log, and a Blockers section.
  • Rules written into PLAN:
    • one commit per phase, with the full suite (npm run ci) run before every commit;
    • never read .env.local or print secrets;
    • tests are the referee: never delete, skip, loosen or re-time a test to get green;
    • stop only if a requirement or AC must change.
  • Tests carry AC IDs in their names (for example AC-57 …), so npm test -- -t "AC-14\b" proves a single AC.
  • The changelog records every spec version:
    • v0.1 (22 Oct): 90 requirements and 82 ACs from the brief.
    • v0.2: decisions Q1–Q13 accepted as defaults, except Q12, where a bright light theme replaced dark-by-default. Added R91 (game colours and avatars), R92 (celebrations with reduced motion), R93 (privacy page) and AC-83–87.
    • v0.3: Vercel became Git-connected and the builder never deploys. Every E2E spec also runs on WebKit iPhone (AC-88 for iOS touch drawing).
    • v0.4 (26 Oct): production DB layer moved to pg with attachDatabasePool; client request timeouts (catch-ups 10 s, actions 30 s with one retry); R94 Sign in at the top, with AC-89.
    • v0.5 (27 Oct): playtest improvements R95–R103 (How-to-play card, Pick for us, presets, WhatsApp share and QR, three new games) with AC-90–AC-103. Deploy checks of record now run from a GitHub-hosted runner, changing AC-80's method but not its measurement.
  • Decisions get logged with a reason, including corrections. The 26 Oct entry blamed production stalls on the Neon pool; a later entry says the probes disprove that and the cause was the network path.
  • The Blockers section is where spec questions go. Example: B1 asked whether AC-80's stroke check should be accepted as intermittent, re-measured, or run elsewhere. The owner chose "run elsewhere", and B1 was resolved after 3 consecutive passing runs.

8. Deployment, environments, secrets, security and privacy

  • Deploy: Vercel is Git-connected and deploys production when main is pushed. vercel.json sets region iad1 (next to Neon US East), build npm run vercel-build (run migrations, then next build), and a daily cron at 03:00 UTC (/api/cron/cleanup) that ends expired rooms and deletes their strokes and presence rows.
  • Environments:
    • Production: Neon main.
    • Preview, local real-services checks (npm run test:real): Neon dev.
    • Tests: a throwaway local Postgres, with test mode on (HUDDLE_TEST_MODE=1). isTestMode() throws if VERCEL_ENV is set, so test mode can never run on Vercel.
  • Secrets: DATABASE_URL, ABLY_API_KEY, AUTH_SECRET and the Google ID and secret live only in .env.local and Vercel env settings. .env.example lists names only, and npm run env:check prints names with set/MISSING, never values. The project rule was that no tool or agent reads .env.local.
  • Realtime auth: the Ably root key never reaches the browser. /api/realtime/token returns a TokenRequest with capability {"huddle:room:<id>":["subscribe"]} and a 60 min TTL, only for a seated identity or a registered screen (403 otherwise). Clients cannot publish.
  • Secrecy: all outgoing data goes through publicView / privateView. Realtime carries only the public view; private data is fetched over HTTPS.
  • Identity: the device token is 32 random bytes in an httpOnly cookie, stored as a SHA-256 hash. Google sign-in uses Auth.js JWT sessions. The test Credentials provider is registered only in test mode.
  • Abuse limits: 10 actions/s and 3 chats per 2 s per seat; stroke batches at most 8 KB and 8 per second per room; 12 seats, 8 spectators and 2 screens per room.
  • Privacy (R93, /privacy): states what is collected (display names, device token, Google name, email and picture, game results), who processes it (Vercel, Neon, Ably, Google), that rooms are kept 24 h after last activity and results until deletion is requested, that there are no ads or trackers, and that contact is via GitHub Issues.
  • Not done, by design (SPEC §9): no content moderation, name filter or reporting of users (admin kick is the only tool), and no anti-cheat beyond server-side validation.

9. Debugging stories (from PLAN's decision log and commits)

The 11th action: the first CI failure (commit e4865c7)

Symptom: CI failed AC-84 on Android: the demo room drifted to the night summary. Evidence: the helper sent two admin actions per demo game, and on the CI runner the 11th action landed 918 ms after the 1st. Root cause: the server's rate limit (R46, 10 actions per seat per second) correctly rejected it, and the demo picker silently ignored the rejection. Fix: an actionPacer helper waits until the 10th most recent action is over a second old, and the picker now shows the error. Regression tests start and end every demo game back to back. Lesson: locally each game took about 250 ms, under the limit, which is why it never failed on the laptop.

WebKit can't load the 7th phone (Phase 15)

Symptom: in 8-phone tests, phones 7 and 8 never loaded on WebKit. Root cause: Playwright's WebKit shares one network process with a 6-connections-per-host limit, and each phone holds an open event stream in test mode. Fix: every 4 phones use a different loopback host name (localhost, 127.0.0.1, [::1]), which WebKit pools separately (tests/e2e/helpers.ts).

The iPhone CI job hung for 40 minutes (37dc613, 8f28c08, 2e15f8b)

Symptom 1: the iPhone job was cancelled at the 40-minute limit with no report. Cause: test budgets of 3–4× the real duration, plus a retry, outlasted the job. Fix: bounded budgets, Playwright globalTimeout 25 min, a step timeout, traces on failure, video only on retry, and the report uploaded if: always().

Symptom 2: later the whole runner stalled and even the timeouts didn't fire. Fix: iPhone sharded into 3 jobs with 1 worker each, the test command wrapped in timeout --signal=KILL 20m, and memory and load logged every 60 s.

Symptom 3: one shard's playwright install --with-deps took 16–23 min. My first retry loop made it worse: the 8-minute cut-off killed npx but not the root-owned apt-get, which kept the dpkg lock, so every retry failed with "Could not get lock". This was visible only after failure tails were added as public annotations. Fix: system packages install once, never cut off, with apt retries and a lock timeout; the browser download (cached) is the step that retries.

Production stalls: first blamed on the database, then on the network (d3b505c, c4df1a7)

Symptom: on production, some requests stalled 15–30 s. First hypothesis: the module-scope Neon WebSocket pool reused dead connections across Vercel invocations. Production moved to pg over TCP with attachDatabasePool, plus client request timeouts. Correction: probes showed connections from the test machine to Vercel's edge dying after 19.2 s (the Windows TCP retransmission limit), including a static CDN file and nextjs.org, but never google.com. So it was the network path, not the database. The decision log records the correction explicitly. What actually helps a phone through such a stall is the client side: timeouts with a same-actionId retry, and snapshot catch-up.

The reloaded phone that missed strokes (42c8598)

Symptom: in AC-80 on production, the phone that reloads mid-turn missed stroke batches. Root cause: it fetched the stroke history before its Ably channel attached, so batches published in between were never delivered, and with no later batch there was no gap to notice. Fix: SPEC §4.2 already said a snapshot taken mid-turn triggers GET strokes?after=lastSeq. The Canvas now does that after every applied snapshot (onCatchUp), and the client refetches a snapshot whenever Ably attaches without continuity (attached with !resumed). Regression test: tests/e2e/draw-catchup.spec.ts. The local SSE driver attached too fast to show the bug.

Phones queueing on the row lock (Phase 15)

Symptom: with six browsers against Neon, private views arrived 14 s late and answers missed the question timer. Cause: every snapshot, tick and heartbeat took the row lock (about 0.9 s each from India). Fix: peekRoom() runs catch-up on an unlocked read and takes the lock only if something is due. Also, phones now tick on safeNow() (a lower bound) and back off after a no-op tick, because slow responses had made the midpoint estimate run ahead and phones ticked early, which fed the queue.

Small but telling bugs
  • Postgres jsonb reorders object keys, so the canvas fingerprint uses a canonical field order.
  • An Atlas bot re-rolled "blank this turn" on every tick, so it never ran out of time and all-bot games never ended. The decision is now made once per turn. In v0.5, demo bots also blank more as the chain grows.
  • Windows reserved ports 54300–54399 after Hyper-V/WSL started, so the test Postgres asks the OS for a free port.
  • Two Truths' lie validation: Number(null) is 0, so a missing lie read as "statement 1". The unit test caught it.
  • Emoji Decode "Venice": it resolved to Dayton, USA, whose alternates include Venice. The puzzle was dropped, and world cities are now pinned to their country.
  • The deploy @skeleton check counted 31 waves. It topped up to 30 while a slow wave was still in flight. It now waits until no action request is in flight and reads the server's count.
The WebKit "button never stable" investigation

Symptom: local full-suite iPhone runs intermittently fail with "element is not stable" or a stale disabled button. Checked: there are no infinite animations; the one-shot pop-ins never move other elements. The same failure happened on the static home page. Conclusion: under full-suite load on the laptop (3 workers, both projects), WebKit stops producing frames, so tests that pass alone fail together. Fixes where the app or test was at fault:

  • video recording only on retry;
  • Draw word choice through the sync client in specs that don't test the button;
  • the How-to-play card lost its pop-in animation and its short test-mode timer, so its button is tappable at once.
In CI, with sharding and one worker per iPhone shard, these tests pass.

★ Give me the 2-minute pitch.

Requirements and SDD

★ What is spec-driven development and how did you apply it?

Write the contract first, then build against it. SPEC.md holds EARS requirements tagged Must or Should and pass/fail acceptance criteria tagged by test type. PLAN.md splits the build into phases, each "done when" named ACs pass, with one commit per phase. Every AC has a test with its ID in the name. Notable choices go in a decision log, spec changes get a version and a changelog row, and anything that would change a requirement stops the work as a Blocker.

Follow-up: Give an example of the spec changing. v0.4 changed the production database layer and added request timeouts after production evidence; v0.5 changed only where AC-80 runs.
What does EARS stand for? Give one example from the spec.

Example, unwanted behaviour: R16, "If the realtime connection has been down for more than 10 s, then the client shall poll the snapshot every 3 s and show a 'Reconnecting…' indicator". Follow-up: Why bother with patterns? Each sentence has one trigger and one response, so it maps to one test.
How do requirements map to tests?

Architecture and request routing

★ Walk me through the architecture.

The phones run a React UI and a sync client. Every action is an HTTPS POST to a Next.js route handler on Vercel, which calls roomOp: one Postgres transaction that locks the room row, replays idempotent actions, catches up overdue deadlines, applies the action through the pure engine and game module, and writes the state with version + 1. After the commit it publishes the public view to the room's Ably channel, and every phone applies it. Private data is fetched over HTTPS by the seats listed in privateFor.

Follow-up: Why publish after commit? So no phone ever sees a state that could still roll back.
What is "pure" about the engine and why does it matter?

src/engine and src/games do no I/O: time and randomness come in through a context (ctx.now, ctx.rng, seeded per room). That makes every game testable in milliseconds with a fake clock, deterministic in tests, and shared by the server, the unit tests and the bot simulations.

Follow-up: Where do side effects go? The engine pushes ctx.effects (game ended, strokes, place suggestion), which applyEffects writes in the same transaction.
What does a game module look like?

GameModule in src/games/types.ts: start, act, onDeadline, publicView, privateView, plus optional bot, shiftTimes, seatRemoved, stats and chatActions. It's registered in registry.ts, and its metadata (settings spec, How-to-play, intro, minimum players) lives in meta.ts.

Follow-up: How long did a new game take? v0.5 added three; each reused the pattern plus wiring into the registry, meta, demo, colours and test helpers.
How are API routes organised?

Under src/app/api: rooms (create), rooms/[code]/{actions, join, snapshot, tick, heartbeat, strokes, qr, screen, crew}, realtime/token (plus stream in test mode), identity/{guest, me, claim}, crews, questions/[id]/report, recap/[roomId]/image, demo, auth/[...nextauth] and cron/cleanup. Each wraps its work in handle(), which turns a GameError into {ok:false, code} with an HTTP status.

Follow-up: Why does every response include serverNow? The client clock estimates its offset from it.
Why one JSON document per room instead of normalised tables?

A room's live state is small (≤ 16 KB public view at 12 players, AC-15) and always read and written as a whole under one lock. A single document makes each action atomic and easy to version and diff. Everything that outlives the room (results, ratings, nights) goes to normal tables.

Follow-up: When would that stop working? If many writers per room contended heavily; the SPEC's fallback is an append-only answers table.
What happens on the big screen?

/screen registers a display-only cookie huddle_screen = roomId.token (at most 2 per room). Requests send x-huddle-screen: 1, and touch() serves only the public view even if the same browser is a player. The screen reuses each game's phone component in a display layout.

Follow-up: How do you test it never sees secrets? AC-55 checks the screen's network log never contains the Draw word.
Explain peekRoom vs roomOp.

roomOp locks the row (FOR UPDATE). peekRoom reads without locking, runs catch-up on a copy, and returns immediately if nothing changed and no effects arose; otherwise the caller falls back to roomOp. Snapshot, tick and heartbeat use peek-then-lock, so a room's phones don't queue behind each other's no-op requests.

Follow-up: Is there a race? If something became due, the locked path re-runs catch-up on fresh state, so peek never writes anything.
How does the client decide what to fetch?

onStateMessage: if v ≤ local, ignore it; if v = local + 1, apply the public view, and fetch a snapshot if my seat is in privateFor; if there's a gap, fetch a snapshot. It also fetches on first load, Ably connected or attached without resume, visibility, focus, online and pageshow. Snapshot fetches coalesce, and a fetch requested during another runs once afterwards.

Follow-up: What if a response is older than a message already applied? It refetches so the private view is current too.

Realtime sync and Ably token auth

★ How does realtime work, and how are clients authenticated to Ably?

Each room has one Ably channel, huddle:room:<roomId>; the UUID is used rather than the code so codes can be reused. Phones connect with authUrl=/api/realtime/token?code=…. The server checks the caller is seated (or a registered screen) and returns a TokenRequest signed with the server key, with capability subscribe on that channel only and a 60 min TTL. Clients can't publish; the server publishes via the Ably REST API after each commit.

Follow-up: What stops a kicked player listening? The token route refuses kicked or unseated identities (403), and nothing secret is on the channel anyway.
What travels over Ably and what doesn't?

Two message names: state ({v, serverNow, public, privateFor}) and strokes ({turnId, seq, ops}). Secrets never travel over Ably: a seat whose private view changed fetches it over authenticated HTTPS, and feedback meant only for the actor (like "you're close") comes back in that action's own response.

Follow-up: Why not encrypt private data on the channel? Fetching it over HTTPS is simpler and keeps the key out of browsers.
What happens when Ably drops a message?

The next message has a version gap, so the client fetches a snapshot. If no further message comes, the heartbeat catches it: it returns the current v, and a higher one triggers a snapshot. The heartbeat runs every 20 s in production. Focus, visibility and online events also resync. AC-16 drops 3 messages on purpose and expects a snapshot within 1 s.

Follow-up: So the worst case is about 20 s stale? For a lone missed message with no later activity, yes; that may be what deploy-checks run #4 saw (see curveballs).
What if realtime is down altogether?

If Ably hasn't connected for 10 s, or the browser reports offline, the client polls the snapshot every 3 s and shows "Reconnecting… (still playing)" (R16). The game stays fully playable; AC-20 plays a 3-question quiz with realtime blocked.

Follow-up: Does polling hammer the database? Polls go through peekRoom, an unlocked read, and a few phones × 1 every 3 s is small.
Why a local SSE driver in tests?

CI has no Ably secrets, and tests must be deterministic and offline. REALTIME_DRIVER=local uses an in-process EventEmitter served as server-sent events (/api/realtime/stream), which returns 404 outside test mode (checked by AC-77). Real Ably is exercised by test:real and the deploy checks.

Follow-up: Did the difference ever hide a bug? Yes: the reloaded-phone stroke bug only showed on Ably, because SSE attached too fast.
How do clients agree on the countdown?

Every response carries serverNow. ServerClock estimates offset = serverNow − (tSend + tRecv)/2 from the lowest-RTT of the last 5 samples, and the countdown is computed from the server deadline. AC-22 holds within 500 ms with ±90 s skew and 50–400 ms RTT; AC-23 checks two phones with clocks 60 s apart.

Follow-up: Why the lowest RTT? The midpoint assumption is most accurate when the trip is shortest and most symmetric.
How are Draw strokes kept in order and complete?

The drawer assigns a monotonic seq per turn. The server inserts with ON CONFLICT DO NOTHING (idempotent) and publishes; viewers render in seq order. A gap, a reconnect or any applied snapshot triggers GET strokes?after=lastSeq. AC-17 reloads and reopens phones mid-turn and expects the full drawing within 3 s.

Follow-up: Why aren't strokes in the room state? They're high-frequency; keeping them off the locked row keeps actions fast.
What's the Ably budget?

SPEC §7 estimated about 110,000 messages per 3-hour 8-player night (×10 including deliveries), against roughly 6 M a month on the free tier. The probe measured a projected 79,680 per night, 1.33 % of 6 M (AC-81 requires ≤ 5 %). Strokes dominate: batching every 200 ms and RDP keep publishes around 4–5 per second while drawing.

Follow-up: What if you exceeded it? The SPEC's fallbacks are a slower flush, a larger ε, or the drawer publishing directly on a turn-scoped token.

Server as referee

★ Why make the server the referee instead of trusting clients?

Fairness and secrecy: the server holds answers and words, validates every action against the current phase and turn, and sends each viewer only what they may see. It also gives one source of truth for rejoining phones; a client can always replace its view with a snapshot. R11: every action goes through an API route that validates it, saves it with version + 1, and publishes only after the commit.

Follow-up: What does it cost? A round trip per action (about 200 ms from US East, about 850 ms from India), which is why the UI shows taps optimistically.
What does "invalid action" mean and what happens?

Wrong phase, not your turn, malformed, or paused. The module throws GameError (WRONG_PHASE, NOT_YOUR_TURN, INVALID, PAUSED); the transaction rolls back and the client gets the code. AC-13 checks, for every game through the real database pipeline, that state and version are unchanged.

Follow-up: Is the error shown to users? Yes, where it matters, for example Atlas reasons or the demo's "Too many taps".
How do you avoid double-applying a retried tap?

Every action has a client UUID. The server checks room_actions under the row lock: a known id returns the stored result. The client retries once on a timeout with the same id, so a slow tap waits rather than being dropped or doubled.

Follow-up: And concurrent taps from different phones? The row lock serialises them; AC-14 sends 20 at once and expects exactly +20 versions.
Who decides the score?

Only the server, in the module's act or onDeadline, via award(), which records an undoable ScoreEvent. Timing for speed points uses server time (ctx.now − phase.startedAt), not client clocks.

Follow-up: Except Charades? Right: the actor's "Guessed" tap is trusted by design (Q10), and the admin's Undo fixes mistakes.
What stops a player from cheating via DevTools?

Nothing secret reaches them before the reveal: views are built per viewer, realtime carries only the public view, and AC-38/AC-39 search every payload for secrets. They can call the API directly, but the same validation applies. Peeking at a friend's screen is an accepted non-goal.

Follow-up: Could they spam? They'd hit the rate limit (R46).

Room-row locking and versioned snapshots

★ How do you handle concurrency when several phones act at once?

Each room is one row. Every state change runs in a transaction that starts with SELECT … FOR UPDATE, so actions on the same room are serialised and each sees the latest state; different rooms never block each other. After the change, version increases by 1, so clients can detect missing updates.

Follow-up: Isn't locking slow? Transactions are short and strokes stay off the row; production action p95 is about 200 ms from US East.
What is the version used for?

Gap detection (a client at v5 receiving v7 fetches a snapshot), ordering (anything ≤ local is ignored), and the heartbeat (a higher v means "you're behind"). It equals rooms.version, and state.v mirrors it.

Follow-up: Does every request bump it? Only if the state actually changed (a JSON comparison of before and after).
What's in a snapshot?

snapshotFor(): {v, public: publicView(…), me: privateView(viewer)}, plus the realtime driver and channel and heartbeatMs. The private part holds the seat, role, admin flag and the game's private view (for example my word, my choice, my answers). AC-15 checks a snapshot equals those functions exactly, and an unknown viewer gets the public view only.

Follow-up: Why does the snapshot route sometimes write? It runs catch-up, so if a deadline passed it advances the game.
What does privateChanges do?

It compares each seat's private view before and after an operation and lists the seats whose view changed. That list is privateFor in the realtime message: only those phones fetch a snapshot. It's rare in practice: a new question, a word choice, a guessed-only chat line.

Follow-up: Cost? It builds two private views per seat per change; fine for at most 12 seats.
What if two phones both think they're first to end a timer?

Both send a tick; the first takes the lock and processes the deadline, which bumps phase.id. The second finds nothing due and is a no-op. AC-24 sends 5 parallel ticks and expects exactly one transition.

Follow-up: Why random jitter? 0–300 ms of jitter spreads phones out so they don't all hit at once.
How big can the state get?

The public view is checked at ≤ 16 KB at every step of a 12-player game for every game (AC-15). Notices are capped at 10, and Atlas shows the last 30 places. Finished results move to tables; scoreEvents covers only the current game.

Follow-up: Why 16 KB? It keeps realtime messages comfortably small (Ably allows much more).

Server timers and deadline processing

★ Vercel has no background process. How do timers work?

Every timed phase stores an absolute server-time deadline. Nothing runs at that moment; instead any request processes overdue deadlines first (catch-up). Phones know nextWakeAt (the earliest of the deadline and the next bot action) and send a tick once it has certainly passed on the server (safeNow plus jitter). So the game advances as long as one phone is open, and catch-up chains overdue turns in order, up to 50 steps.

Follow-up: And if every phone is off? Nothing advances; when someone returns after over 120 s of silence, the game auto-pauses instead of fast-forwarding (R20).
Why is catch-up run "at each deadline's own time"?

So a chain of overdue turns behaves exactly as if someone had ticked each one: each step sets ctx.now to its own deadline (a virtual clock), so the timing and AFK accounting are right. The decision log records this for Phase 2.

Follow-up: Why cap it at 50? To bound the work of one request.
How does pause/resume keep the exact time?

Pausing stores remainingMs; resuming sets deadline = now + remainingMs, shifts any visible end time and bot due times, and calls the module's shiftTimes. AC-28: pausing with 37.4 s left and resuming 5 minutes later gives exactly 37.4 s.

Follow-up: What's shiftTimes for? Draw keeps hint times inside its state; they shift too.
What's the difference between deadline and endsAt?

In Draw, hints are timed events inside the drawing phase: deadline is the next wake-up (a hint), while endsAt is the visible countdown end. The countdown shows endsAt ?? deadline, so it never jumps.

Follow-up: Could you use separate phases for hints? It would change the phase id and the turn semantics; the decision log explains the choice.
Why do phones use safeNow rather than the clock offset for ticks?

serverNow is stamped as the response leaves, so slow responses made the midpoint estimate run ahead and phones ticked early and repeatedly, which fed the row-lock queue. safeNow is a lower bound (serverNow − tRecv), and after a no-op tick the phone backs off 1–2 s.

Follow-up: Then why does the countdown still use the midpoint? For display accuracy (AC-22); being early by a few ms on screen is harmless.
How does the How-to-play card fit the timer model?

It's an engine phase intro with a 20 s deadline. The game module's start() runs only when the deadline passes, every active human taps Got it, or the admin skips. While it shows, the game state is null and game actions return WRONG_PHASE.

Follow-up: Why not a client overlay? A client overlay would hide a running question timer.
How do bots fit in?

planBots asks each bot's module for its next action and a delay, and stores {seatId, dueAt, phaseId, action} in botPlan. Catch-up runs due bot actions in time order with deadlines. A plan for an old phase is discarded.

Follow-up: Bug story? An Atlas bot re-rolled "blank" on every tick and never timed out; the decision is now stored per turn.

Secret filtering per viewer

★ How do you make sure secrets don't leak?

Every outgoing payload goes through one function pair: publicView (safe for anyone) and privateView(seat) (only what that seat may see). Realtime messages carry only the public view. SPEC §4.4 lists each secret and who may see it. Tests: AC-38 drives every phase of every game and searches public, screen and non-entitled views for each secret; AC-39 records every HTTP response and realtime frame on real browsers and searches them; AC-6 scans bundles for sentinel server secrets.

Follow-up: Give an example. The quiz public view includes reveal only during the reveal phase, and the correct index never appears before then.
How does Draw handle the chat of players who already guessed?

Once you've guessed correctly, your messages go to a secret chat seen only by the drawer and other correct guessers (R74). Others see "<name> guessed it!" without the text. Near misses get a private "You're close!" in the action response only.

Follow-up: Can the drawer chat? No, drawer chat is rejected.
How is the imposter kept secret?

Each player's private view contains only their own word. The imposter's identity isn't in any view until the reveal; by default even the imposter isn't told (Q2). AC-73 checks each phone shows exactly one word and exactly one phone's word differs.

Follow-up: Can the imposter be told? Yes, an "Imposter knows" house rule.
Most Likely To says votes are anonymous. How literally?

Literally: individual votes live in state only until the tally, then s.votes = {}. Views carry only totals, and a phone is told only whether it voted, never for whom. AC-74 checks neither the state, the database nor any view holds voter→votee pairs after the tally.

Follow-up: And during the vote? They're in the server's state for that one phase only, never in a view.
How do the new games handle secrets?
  • NPAT: answers exist in views only after the writing ends.
  • Emoji Decode: the answer appears only at the reveal, and guesses are never broadcast.
  • Two Truths: drafts are private, statements appear shuffled on the author's turn, and the lie's position and the votes appear only at that turn's reveal; only the author's view marks the lie.

All three are in AC-38's per-phase secret checks.

Follow-up: Where is the shuffle stored? In server state (perm), so a reload shows the same order.

Rejoin, AFK, admin and spectators

★ How does a phone come back to the same seat and score?

Seats belong to identities, not connections. A guest has a device cookie (huddle_dt, 1 year, httpOnly); a signed-in user has a profile, plus aliases for merged guests. joinRoom finds an existing seat for any alias and returns it unchanged. The phone then fetches a snapshot with the same seat, score, timer and full drawing, because the state lives on the server. AC-18 checks no code path changes scores on rejoin, 5 times at every phase of every game.

Follow-up: What if they open it in a different browser? "That's me" on the disconnected seat, approved by the admin (R17).
How does AFK work?

A turn or answer phase that expires without the seat acting counts a miss. Two consecutive misses set afk; AFK seats' turns are skipped immediately, they're excluded from "everyone has answered", and they keep their seat and score. Any action or "I'm back" clears it. Admin skips don't count as misses.

Follow-up: Exception? In Atlas, AFK players keep their turns and lose lives normally (AC-27).
How does admin hand-off work?

During catch-up, if the admin hasn't been seen for 60 s (presence) or is AFK, admin passes to the connected, non-AFK human seated player with the earliest joinedAt, with a notice. AC-31 closes the admin's page and checks the next player gets the controls.

Follow-up: Can bots become admin? No, candidates exclude bots.
What happens to someone who joins mid-game?

They become a spectator with seatAtNextRound and see the live public view. seatWaiting() seats them at the next round boundary of that game (Quiz: next question; Atlas: next game), joining the smallest team in team games. AC-11 checks a 5th player gets 0 points at question 3.

Follow-up: Room full? Above 12 seated, newcomers can only watch (up to 8 spectators).
What can the admin do?

Skip a turn, kick, pause and resume, end the game, transfer admin, undo the last score (repeatable back to the start of the game), set the queue, teams and rules, rematch, and end the night. Every admin action shows a notice; non-admins get NOT_ADMIN (AC-29).

Follow-up: Is the admin required? No: R28 says the whole queue runs from deadlines alone (AC-33 closes the admin's tab right after starting).
Kicking: what if the kicked player was mid-turn?

kick marks the seat kicked, removes them from teams, claims and bot plans, and calls the module's seatRemoved to repair turn order (Atlas moves on; Two Truths skips their turn). They see "Removed by the admin", and a rejoin returns KICKED (AC-12).

Follow-up: Can they still listen to realtime? No new token is issued to a kicked seat.
What if a signed-in user opens the room on a second device?

Opening the room makes that device active (deviceId on the seat). The other device shows "Your seat is now active on another device" with a "Use here" button. AC-3 checks the score carries over.

Follow-up: Why track device? To avoid two phones acting as one seat by accident.

Rate limiting

What are the limits and where are they enforced?

rateLimit() in engine/room.ts, inside the locked transaction: at most 10 actions per second per seat, and 3 chat-type actions per 2 s (each module declares its chatActions, like Draw guesses or Emoji guesses). Stroke batches are limited separately to 8 per second per room. Excess returns RATE_LIMITED (HTTP 429).

Follow-up: Where are the timestamps kept? In the room state (rate, chatRate), pruned to the window.
Did the rate limit ever cause a bug?

Yes, in a test: the first CI run sent 11 admin actions within a second, and the 11th was correctly rejected while the demo picker hid the error. The fix paced the test and made the UI show the rejection.

Follow-up: Why not raise the limit? The limit is correct product behaviour; the test was outrunning it.
Is rate limiting per IP?

No, per seat inside a room (and per room for strokes). Players are identified by seat, and serverless instances don't share memory, so the state row is the natural place for it.

Follow-up: Room creation spam? Not limited per IP in this build; it's a known gap. Rooms expire after 24 h.

Team balancing (Elo and snake draft)

How are teams balanced?

Each player's strength is their Elo for this game, else the mean of their other game ratings, else 1000. Sort by strength, snake-draft into k teams (1-2-2-1…), then repeatedly apply the single cross-team swap that most reduces the gap between the highest and lowest team mean, until no swap helps. It's deterministic for a given input order. Example: 1400–900 in steps of 100 into 2 teams gives means 1166.7 vs 1133.3.

Follow-up: Why not try all splits? Snake plus swaps is near-optimal for ≤ 12 players and trivially fast; AC-35 requires means within 34 points.
Explain multiplayer Elo.

Treat every pair as a match: the expected score is E = 1/(1+10^((Rj−Ri)/400)), the actual S is 1, ½ or 0 by rank. Then ΔR = (K/(n−1)) × Σ(S−E) with K = 32. Beating stronger players earns more; with two players it's classic Elo (+16/−16 for equals). Deltas sum to about zero (AC-37).

Follow-up: Team games? Every member carries the team's rank.
How are teams assigned to late joiners?

To the smallest team (seatWaiting / joinRoom), so sizes stay within one.

Follow-up: Can the admin override? Yes: move, shuffle or rebalance in the lobby (AC-36).
Where do ratings come from at runtime?

prepare() in rooms.ts loads ratings rows for the room's identities when no game is running; balancing never trusts client-supplied ratings. After each game, recordRatings updates them once (the game insert is unique per room and game number).

Follow-up: Bots? They have no identity rows, so they're skipped.
What are placement points versus ratings?

Placement points (0–100 by finishing position, ties averaged) rank crew seasons. Ratings (Elo) only balance teams. Most Likely To gives no placement points (Q6).

Follow-up: Why two systems? Seasons should be easy to read; balancing needs skill estimates.

Each game's rules module

Quiz Clash: scoring and fairness?

The first tap is final (Q7). Correct scores 500 + round(500 × remaining/total), timed by the server from the phase start; wrong or none scores 0; team mode averages members. Questions don't repeat in a room until the pool is exhausted, and 3 reports exclude a question (R60). A question ends early when all active players have answered.

Follow-up: Correct at the start? 1000; at the deadline 500 (AC-57).
Draw & Guess: what's special technically?

Strokes bypass the room lock (append-only table, no versions); the canvas uses pointer events and touch-action: none, so iOS doesn't scroll or zoom (AC-88). Hints are timed inside the phase, the mask shows _ _ _, and at most half the letters are revealed. The drawer chooses within 15 s or the turn is skipped as a miss.

Follow-up: Bot drawings? 24 parametric drawings generated by scripts/make-bot-drawings.ts.
Atlas: how is a place validated?

checkPlace looks up the folded text in an index of names and alternates from data/places.json (9,766 GeoNames places plus a curated list of Indian states and old names). It checks the start letter, the variant (any, India only, countries only), and that the place (by id, so Bombay = Mumbai) is unused. Unknown names pause the timer for a 10 s accept vote: a majority of votes cast accepts.

Follow-up: The letter fallback? If no unused place starts with the last letter, it uses the one before it, and so on (nextLetter).
Imposter: walk through a round.

Secret words go out (1 imposter, or 2 at 8+ players if enabled). Clue rounds take one word each, no own word and no spaces. Then discussion (ends early when all are Ready), a vote excluding self, and a 20 s revote on a tie (a second tie means the imposter survives). A caught imposter gets 30 s to guess the crew word and steal. Scores: crew win +100 each, +50 per correct voter, imposter survives +300, steal +200.

Follow-up: Multiple rounds? 1–5 rounds (default 3), with new words and a new imposter each time (decision log).
Dumb Charades: how does the steal rule work?

If the steal rule is on and a turn times out, the actor gets 15 s to mark which other team guessed; that team gets 5 points, then the title is revealed (R65). The actor's taps are trusted (Q10).

Follow-up: What else does the actor see? Year, industry, era and word count (decision log).
Most Likely To: why no points?

It's a social game: results are recorded with excludeFromSeason and zero placement points (Q6). Night stats still show who collected the most votes.

Follow-up: Reveal animation and reduced motion? Totals appear one by one over about 5 s; with reduced motion, all at once.
Name Place Animal Thing: how is it judged?

buildItems groups equal answers per category, folding text and grouping places by database id. A wrong first letter scores 0 with no vote; a known place is valid at once; everything else stands unless more than half of the other active players reject it (standsAfterVote: rejects × 2 ≤ voters). Unique valid answers score 10, shared ones 5 each.

Follow-up: Why "reject" rather than "accept" votes? With 4–5 categories × several players, per-answer accept taps would take minutes.
Emoji Decode: how does matching work?

isCorrect folds the guess and drops a leading "the". It accepts the answer or any alternate within a typo allowance (1 edit from 5 letters, 2 from 10), and for places any name the Atlas database maps to the same place id. World cities carry a country code so a same-named city elsewhere doesn't count. The bank has 246 puzzles; a content test forbids flag emoji and letters in clues.

Follow-up: Short answers? They must be exact: "Up" won't accept "Upp".
Two Truths & a Lie: flow and scoring?

Everyone writes three different statements (≤ 80 characters) and marks the lie (autosaved drafts). Then each author in seat order: statements are shuffled (perm) and the others vote once. At the reveal, spotting the lie scores +100 and the author +50 per player fooled. Non-submitters are skipped, and non-voters count a missed turn.

Follow-up: Bug found? Number(null) = 0 made a missing lie read as statement 1; the validation now requires a number.
How does a new game automatically get tested for the hard properties?

Adding its id to GAMES in tests/helpers/drive.ts enrols it in the cross-game suites: AC-38 secrets (with a per-game case), AC-15 view size at 12 players, AC-18 rejoin, AC-32 settings, AC-46 How-to-play and AC-13 invalid actions. E2E adds it to the demo (AC-47), accent (AC-84), layout (AC-40), contrast (AC-41) and leaderboard (AC-42) loops.

Follow-up: Did that catch anything? Yes: an NPAT colour at 4.49:1 contrast failed AC-83 before it shipped.

Frontend, design and accessibility

What does the frontend look like structurally?

Next.js pages: / (home), /r/[code] (room), /demo, /screen, /c/[invite], /crews/[id], /about, /privacy, /signin and /offline. The room page uses RoomClient (join, then live), then RoomView (lobby, playing, break or summary), then a per-game component from src/client/games. State comes from RoomSync via the useRoom hook.

Follow-up: State library? None: a small subscribe/notify class; the server is the store.
How did you design for accessibility?

WCAG 2.2 AA contrast in both themes, checked two ways: a unit test over design tokens (AC-83) and axe-core in E2E on the home page, lobby, each game's main phase and the scoreboard (AC-41). Primary buttons are at least 48 × 48 px at 360 px width with no horizontal scrolling (AC-40). Reduced motion removes confetti and limits animations to 150 ms (AC-85). Statuses use role="status" and timers role="timer".

Follow-up: Colour-blind players? Correctness is shown with ✓ and text, not colour alone; avatars also differ by emoji.
Why light by default?

Decision Q12, recorded in SPEC v0.2: a bright party theme fits the product, whatever the OS setting. Dark is a toggle remembered per device. AC-41 checks the first visit is light even when the OS prefers dark.

Follow-up: How do game colours work? [data-game=…] sets --accent, --on-accent, --accent-soft and --accent-ink; nine distinct hues.
What iPhone-specific work was needed?

Using dvh/svh instead of 100vh, safe-area insets with viewport-fit=cover, Apple touch icon and meta tags, and no page scroll or zoom while drawing. Vibration is feature-detected, so iOS degrades silently (R40). Every E2E spec also runs on WebKit.

Follow-up: Biggest WebKit surprise? The 6-connections-per-host limit in Playwright's WebKit, and frame stalls under load.
How do you avoid inputs losing typed text during updates?

Typed text is local React state; server updates don't overwrite it. NPAT and Two Truths seed the form once per round from the server draft (keyed by round) and autosave a second after typing stops. The leaderboard overlay is non-modal and keeps the game mounted, so typed guesses survive (AC-42).

Follow-up: Why autosave? So a timer ending mid-word still counts what was written.
Why no layout shift on interactive elements?

Playwright and real fingers tap where the button is. One-shot pop-ins don't move other elements, and the How-to-play card has no entrance animation so its button is tappable immediately. That was a fix after a WebKit "not stable" failure.

Follow-up: Any infinite animations? No, checked explicitly (decision log, POLISH task).
How did you review the visual design?

scripts/ui-audit.ts takes full-page screenshots of every screen and game phase at 360 px and 1440 px in light and dark. The polish pass (commit 7399458) came from critiquing those: notices moved off the inputs, the correct answer shown at full strength, empty states added.

Follow-up: Automated? The audit is a script; the critique was a human-style review of the shots.

Database

Which tables matter most and why?

rooms (live state and version), room_actions (idempotency and audit), presence (kept apart so heartbeats never lock the room), strokes (append-only), and games / game_results / nights / ratings (kept forever, independent of room expiry, R45).

Follow-up: Why a separate presence table? Heartbeats every 20 s from every phone would otherwise version and lock the state row.
How are migrations run?

scripts/migrate.ts applies db/migrations/*.sql under a transaction lock; Vercel runs it in vercel-build before next build. Locally, npm run db:migrate uses node --env-file, so no tool reads the env file directly.

Follow-up: How many migrations? One, 001_core.sql; all tables were created up front.
How do codes stay unique yet reusable?

A partial unique index on rooms(code) WHERE ended_at IS NULL. On create, an expired room holding the code is retired first, and a collision retries. After 24 h of inactivity a room expires, and the daily cron ends it.

Follow-up: What survives expiry? Games, results and nights (AC-10).
How is "exactly once" guaranteed for results?

games has a unique (room_id, game_no); recordGame inserts with ON CONFLICT DO NOTHING and only then writes results and ratings. Processing the same end twice writes nothing new (AC-48).

Follow-up: Inside the same transaction? Yes, effects are applied before the commit.
What's the connection setup on Vercel?

pg.Pool with max 10 connections, a 30 s connection timeout and keepAlive. On Vercel it adds a 5 s idle timeout and attachDatabasePool, so idle connections close before an instance is suspended. It connects to Neon's pooled endpoint.

Follow-up: Why 30 s? It matches the client's 30 s action timeout, so a burst queued on one room's lock waits instead of failing.

Security and privacy

How do you handle secrets and keys?

Server keys (DATABASE_URL, ABLY_API_KEY, AUTH_SECRET, the Google secret) exist only in .env.local and Vercel env settings, and are read only in server modules marked server-only. The browser gets short-lived, subscribe-only Ably tokens. CI builds with sentinel secrets, and AC-6 scans every bundle, response and realtime frame for them. The working rule was that no tool or agent ever reads .env.local; env:check prints names only.

Follow-up: Can test mode be enabled in production? No: isTestMode() throws if VERCEL_ENV is set.
How are guest identities secured?

A random 32-byte token in an httpOnly, SameSite=Lax cookie (Secure over HTTPS), valid for a year. The database stores only its SHA-256 hash, so a database leak doesn't give working tokens.

Follow-up: If someone copies the cookie? They'd be that guest; it's a party game, and a signed-in Google profile is the stronger option.
What personal data do you hold?

Display names, the device token (hashed), and Google name, email and picture if you sign in, plus game results. It's processed by Vercel, Neon, Ably and Google. Rooms are kept 24 h after last activity; results until deletion is requested via GitHub Issues. There are no ads or trackers (R93, AC-86).

Follow-up: Why a privacy page at all? Google's OAuth consent screen requires a public privacy policy.
Why no word filter on names?

A deliberate non-goal: names are any 1–24 characters in any script, including emoji (R1, AC-1 even tests that a rude word is accepted). Moderation is out of scope for private rooms of friends; admin kick is the tool.

Follow-up: Risk? Acceptable for private rooms by code; it would need revisiting for public matchmaking (also a non-goal).
How do you protect against XSS from player text?

All text is rendered through React, which escapes it; no player input is inserted as HTML. Inputs are length-capped on the server (for example Atlas 60 characters, NPAT answers 30, statements 80).

Follow-up: Security headers? poweredByHeader is off. No custom CSP was configured in this build; it's a possible improvement.
Who can call the cron endpoint?

If CRON_SECRET is set, it requires Authorization: Bearer <secret>, as Vercel Cron sends. The job only ends expired rooms and deletes transient rows.

Follow-up: Is it idempotent? Yes, running it twice is harmless.

Testing and CI (including the WebKit stall investigation)

★ How do you test a multiplayer game?

Two levels. Unit: the pure engine through a harness with a fake clock and seeded RNG, and bots driving every game to the end while checking secrecy, view size and rejoin at every step. E2E: Playwright opens up to 8 browser contexts as separate phones against a production build in test mode, and checks every phone shows the same thing (for example AC-58: 4 phones, identical scoreboards within ±1 point). Every E2E spec runs on Android Chromium and iPhone WebKit. Then deploy checks run against production.

Follow-up: How do you avoid flaky timing? Seeded RNG, short test-mode timers, waiting for state (versions, test ids) instead of sleeping, and pacing actions under the rate limit.
★ Tell me about the WebKit stalls.

Four separate issues:

  1. A WebKit connection limit. Phones 7 and 8 never loaded, because Playwright's WebKit shares a 6-connections-per-host limit and each phone holds an event stream. Fix: a different loopback host name per 4 phones.
  2. A CI job hanging to its 40-minute limit with no report. Fix: bounded budgets, a global timeout, a step timeout and always-uploaded reports.
  3. A whole runner stalling with 2 WebKit workers. Fix: 3 shards with 1 worker, a hard kill at 20 min, and memory and load logging.
  4. "Button never stable" locally under load. No infinite animations; it even happened on the static home page, so it's WebKit not producing frames. The app and test fixes: video only on retry, Draw choices via the sync client, no entrance animation on the How-to-play card.
Follow-up: How do you know it's environmental? The same specs pass alone and in CI's sharded jobs, and fail only in the full local run with both projects.
What's the difference between Unit, E2E and Deploy ACs?

Unit: Vitest, including API handlers against a local Postgres. E2E: Playwright with several contexts against a local production build in test mode, on both device projects. Deploy: checks against the production URL after a push. Manual: a human check (only two).

Follow-up: Why a production build for E2E? To test the real bundle, including the secret scan.
How did CI evolve?
  • It started as one job running everything (about 20 minutes).
  • Then it was split into checks and an e2e matrix per device.
  • Then it got budgets, timeouts and always-uploaded reports.
  • Then iPhone was sharded 3 ways with a hard kill and resource logs.
  • Finally the browser installs were made robust: packages installed once with apt retries, and a cached, retried browser download.

Recent green runs take about 0.9 min for checks and 6–14 min per E2E job.

Follow-up: Retries? Only Playwright retries: 1 in CI; never a loosened assertion.
What are the deploy checks and where do they run?

AC-77 (Ably token and update latency), AC-78 (state survives a redeploy), AC-79 (Google redirect), AC-80 (six real browsers: 2 Chromium, 2 Firefox, 2 WebKit; 3 quiz questions and a Draw turn with a reload), AC-87 (demo under 2 minutes), plus the probe (AC-81). Since v0.5 the evidence of record comes from the manual deploy-checks GitHub workflow; laptop runs from India are extra real-world evidence.

Follow-up: Why a manual trigger? Production checks create real rooms and Ably traffic, and they're meaningful after a deploy, not on every push.
How do you prove no secret leaks in the real bundle?

scripts/build.ts builds with sentinel values like sentinel-ably-secret-d0-not-ship. AC-6 searches .next/static, every HTTP response and every realtime frame from a full E2E session for them and for the database URL and password.

Follow-up: And game secrets? AC-39 sniffs the network per phone during real games.
How did tests catch real bugs during the v0.5 round?
  • A missing lie accepted as statement 1.
  • A Quick preset estimating the same minutes as Normal.

Follow-up: Any you fixed by changing a test? Only where the test itself was wrong, like a race in the deploy wave count, and that's logged.
What's the slowest test and why?

The solo-demo test (AC-47) plays all nine games alone with bots: about 6 minutes locally, with a 600 s budget. The full-night regression plays 8 phones through six games with reloads, a Wi-Fi drop, an AFK player and the admin leaving (about 4–5 minutes).

How do you run one AC?

npm test -- -t "AC-57\b" for Unit, npm run test:e2e -- --grep "AC-66\b" for E2E, both projects. The full suite is npm run ci: lint, typecheck, unit, build, E2E.

Performance, latency and scalability

★ What are your production latency numbers?

The budget is 1 s at p95. From the GitHub-hosted runner: action to other phone p95 190–215 ms, stroke end to all viewers p95 324–364 ms, probe delivery p95 98–135 ms. From my laptop in India: actions about 830–860 ms; strokes 838–1355 ms, passing 2 of 5 runs, which is why AC-80's evidence now comes from the runner.

Follow-up: Why is India 4× slower? Round trips to US East plus a network path that drops connections for about 19 s roughly once a minute.
★ What if 1,000 rooms play at once?

The design scales horizontally: each room is its own row and channel, so rooms never contend; serverless functions scale out; Postgres handles many independent row locks. The real limits are the free tiers: Ably Free caps concurrent connections at about 200 (SPEC §7), so roughly 20–25 full rooms, and Vercel Hobby is non-commercial. For 1,000 rooms (around 8,000 phones) you'd need a paid Ably plan, a bigger Neon compute and pool, and Vercel Pro. You'd also watch the per-instance pool (max 10) and lock hold times.

Follow-up: What breaks first technically? Ably connections, then database connections; the per-room design itself doesn't change.
Why does a room's state live in one row, and what about lock contention?

With at most 12 players, a few actions per second per room are fine: transactions are short and strokes, presence and polling avoid the lock (append-only table, separate table, unlocked peek). SPEC §10's fallback is an append-only answers table merged at the reveal if contention ever showed.

Follow-up: Did it ever show? Yes, early on, from no-op requests; that's why peekRoom exists.
How did you keep drawing cheap?

Batching every 200 ms or 64 points, RDP simplification (at least 40 % fewer points), integer delta encoding, batches at most 8 KB, no state lock or version per batch, and at most 8 batches per second per room. The probe measured 4.15 publishes per second on average and 120-byte batches.

Follow-up: Quality loss? Bounded at 1 unit of Hausdorff distance (0.1 % of the width).
What's the bundle-size budget?

SPEC §3: each route's first-load JS at most 250 KB gzipped. Ably is imported dynamically only when realtime connects (await import('ably')), and server-only modules never ship to the browser.

Follow-up: Do the game banks ship to clients? No: rules modules with answers are server-only; clients get views.
Where's the server, and why?

Vercel region iad1 (US East), next to the Neon database in AWS US East 1, so every database round trip inside a request is short. Players' distance shows up only once per request.

Follow-up: Move it to Mumbai? It would need the database there too; it's future work, constrained by free tiers.

Failure scenarios

★ What happens if Ably goes down?

Publishing fails silently on the server (logged, not fatal), and phones notice realtime isn't connected. After 10 s they poll the snapshot every 3 s and show "Reconnecting… (still playing)". The game stays playable, just with up to about 3 s of lag (R16, AC-20). When Ably reconnects, the client fetches a snapshot and switches back.

Follow-up: Drawing during an outage? Strokes are stored; viewers catch up with GET strokes after each snapshot.
What if Neon is down or slow?

Requests fail or wait (up to a 30 s connection timeout). No committed state is lost because each action is one transaction. The client times out catch-ups at 10 s and actions at 30 s, retrying an action once with the same id, so a slow tap waits rather than double-applying. When the database is back, the next request catches up the deadlines.

Follow-up: Cold start? AC-78: the first request after idling succeeds; first loads measured 0.5–2 s.
What if a phone's network stalls for 20 seconds?

This was seen in production from the test laptop. Catch-up requests time out at 10 s and retry (snapshot fetches coalesce, so a stalled one can't block later ones). Actions wait up to 30 s with one same-id retry. Realtime-down detection switches to polling, and the browser's offline event shows "Reconnecting…" immediately.

Follow-up: Was that the server's fault? No: the probes showed it hit a static file and another Vercel site too, but never google.com.
What if everyone's phone locks mid-game?

Nothing advances while no requests arrive. When someone returns, if more than 120 s passed since the last human contact, the game auto-pauses with the remaining time as of that contact (minimum 10 s) rather than skipping through turns (R20, AC-25).

Follow-up: And the 60 s admin grace? If the admin is the one missing, admin passes to someone connected.
What if the server crashes mid-action?

The transaction rolls back, and nothing was published, since publishing happens after commit. The client times out and retries with the same action id; if the first attempt actually committed, the stored result is returned.

Follow-up: And if the publish after commit fails? Clients detect the version gap on the next message or heartbeat and fetch a snapshot.

Why there's no AI in an AI course

★ This is an AI course. Why does the app contain no AI?

The AI is in how it was built, not in the runtime. SPEC §3 says "No AI APIs at runtime. All content is written ahead of time and bundled." A party game needs instant, deterministic, free and testable responses: an LLM call per question or judgment would add latency and cost on free tiers, break deterministic tests, and risk leaking or inventing answers. The AI work is the process: spec-driven development with an autonomous coding agent, verified by tests and production evidence, plus AI-written content checked by automated content tests and a report button.

Follow-up: Where would AI fit later? Optionally generating new question packs offline, reviewed and run through the same content checks; still not at runtime.
Was the content AI-generated? How do you trust it?

Yes, the banks were written ahead, and SPEC §10 lists "Claude-written facts are wrong or dated" as a risk. Mitigations: automated content checks (unique ids, valid options, no time-relative words, place answers resolving in the database, no flag emoji), the in-app report button (3 reports exclude a question), and a spot check during the playtest.

Trade-offs

★ Why not run your own WebSocket server?

Hosting is serverless: Vercel functions are short-lived and can't hold sockets, and the free hosting rules out a long-running process. A managed pub/sub (Ably) keeps fan-out off the functions, gives subscribe-only tokens for security, and survives function cold starts. The trade-off is a third-party dependency and quota, mitigated by the polling fallback.

Follow-up: Would a VM be simpler? For sockets, yes; but then you also run the process, scaling and TLS, and pay for it.
Why not Firebase?

Firebase would give realtime and storage together, but the referee logic (validation, secrets per viewer, deadlines) would need Cloud Functions plus security rules. Ad-hoc queries for seasons and head-to-head records are awkward in Firestore. Postgres transactions with a row lock give a simple, testable serialisation point, and the pure engine runs unchanged in unit tests.

Follow-up: Supabase then? Similar trade-off; the chosen split (Neon plus Ably) is explicit, with each on a free tier.
Why polling plus realtime instead of realtime only?

Realtime is the fast path; snapshots are the truth. Phones on real networks lose messages and connections, so every gap, reconnect, focus or heartbeat leads to a snapshot, and polling keeps the game playable without realtime (R16).

Follow-up: Cost? Polls hit the unlocked peekRoom path.
Why accept the latency of server validation for every tap?

Fairness and secrecy outweigh it. The UI marks taps optimistically (for example the quiz shows your choice as pending), and speed points use server time, so latency doesn't make the scoring unfair.

Follow-up: Cheating by delaying? The timer is server-side; late taps are just late.
Why trust the Charades actor's tap?

Decision Q10: the game is played in person, the actor sees the guess happen, and the admin's Undo fixes mistakes. A voting or confirmation flow would slow every turn.

Follow-up: Abuse? Friends can see it; Undo exists.
Why one big E2E suite on both engines when it's slow and sometimes flaky locally?

The evaluator uses an iPhone, and WebKit behaves differently (connection limits, touch, frame scheduling). Running everything on both found real issues. The flakiness is local-load related; CI sharding keeps it green.

Follow-up: Why not real devices? Emulation covers engine differences cheaply; real devices are the playtest.

"Walk me through this code"

Walk me through roomOp.
  1. Begin a transaction.
  2. SELECT id, state, version … FOR UPDATE on a live room, or ROOM_NOT_FOUND.
  3. If an actionId was given and room_actions has it, return the stored result (replay).
  4. prepare(): load presence, clone the state and build the context, adding ratings and reported questions when no game is running.
  5. catchUp(), then the op itself, then planBots().
  6. If the JSON changed: set version + 1, update the state and expiry, and applyEffects(); otherwise just refresh the activity time at most once a minute.
  7. Insert into room_actions, upsert presence, commit.
  8. After the commit, publish state with the public view and privateFor, then any stroke effects.
Follow-up: Why compare JSON rather than track changes? It's simple and exact for one document per room.
Walk me through applyAction.

If the seat is kicked, throw. Rate-limit (chat actions per module). Clear AFK and the missed-turn streak, since any action proves presence. Then a switch on room-level actions (wave, imBack, introReady, setIntros, setAvatar, setQueue, setTeams, start, demoStart, continue, rematch, newQueue, endNight, pause, resume, skip, endGame, undo, kick, transferAdmin, approveClaim/denyClaim); the default goes to dispatchGame, which checks playing, not paused and seated, then calls the module's act.

Follow-up: Where are settings validated? validateQueue calls validateSettings per game spec; test mode allows shorter timers.
Walk me through RoomSync.act.

Generate a UUID, POST {actionId, type, payload} with a 30 s timeout. On a network error or timeout, send again once with the same id; if that fails, return NETWORK. If the response version jumped by more than 1, fetch a snapshot; on any server error, fetch a snapshot too. Return the body, including any private feedback.

Follow-up: Why fetch on error? An error usually means the phone's view was stale (wrong phase).
Walk me through a game module, for example Emoji Decode's act.

Accept only guess in the puzzle phase, with non-empty trimmed text of at most 60 characters, and only if the seat hasn't solved it already. Record that the seat tried. If isCorrect is false, set ctx.private = {correct: false} and return. Otherwise store the solve time, award() 500 + speed bonus, update stats, return private {correct: true, points}, and reveal early if every active player has solved it.

Follow-up: Why ctx.private? Feedback only the actor should see goes back in that action's response, never on the channel.
Walk me through catchUp.

Auto-pause if the room has been silent too long, and hand off admin if needed. Then loop up to 50 times while not paused: find the earliest due bot action and whether the phase deadline is due. Run whichever is earlier at its own time (ctx.now set to its due time): bot actions via dispatchGame, deadlines via processDeadline, which goes to the module's onDeadline (or the break, or the intro). Replan bots after each deadline, restore the real time, and plan bots again.

Follow-up: Bot action error? A GameError from a bot is swallowed; the bot just misses.

★ Is anything known to be broken or uncertain right now?

Your test passed only after rerunning. Isn't that cherry-picking?

The rule is never to loosen, skip or re-time a test to get green, and to fix flaky tests. Reruns were used only where the failure was shown to be environmental: the same spec passing alone and in CI, with the evidence logged. If the spec says 25 s heartbeat and the code does 20 s, which is right?

The code is stricter (more frequent), so it satisfies the intent of a heartbeat at most 25 s apart; it's derived from the presence window (60 s ÷ 3) so a phone is never marked disconnected between heartbeats. It's an honest discrepancy, noted in PLAN; the clean fix is to update SPEC §4.2's wording.

Follow-up: Why didn't a test catch it? No AC asserts the interval; AC-77 asserts update latency, not heartbeat cadence.
Could two players get the same seat?
